# ROS Car 双车协同定位与 UWB 实施计划

## 1. 目标和边界

本阶段使用两辆轮趣 ROS Car，在同一个 ROS1 Melodic 网络中完成：

- 两辆车同时上线、独立控制和独立发布传感器数据。
- 统一时间、话题命名和 TF 坐标系。
- 分别建立轮式里程计与 IMU 融合定位基线。
- 接入并标定 UWB 测距。
- 将车间 UWB 距离作为协同约束，完成离线和在线定位实验。
- 记录可复现实验数据，为后续月球车多源 PNT 和协同定位研究提供地面验证平台。
- 建立一套可以由公开数据集交叉检查、并能迁移到后续仿真的统一数据接口与评价流程。

本阶段暂不要求视觉导航、机械臂控制、复杂编队控制或 Unreal 月面仿真。

## 2. 需要先明确的系统配置

- [ ] 记录两辆车的具体型号和板载电脑型号。
- [ ] 确认两辆车均使用 Ubuntu 18.04 和 ROS Melodic。
- [ ] 记录两辆车当前的底盘启动命令和 launch 文件位置。
- [ ] 确认轮速数据来源，即电机编码器或底盘里程计。
- [ ] 确认 IMU 型号、发布话题、频率和坐标系。
- [ ] 确认 UWB 型号、通信方式、测距模式和可用节点数量。
- [ ] 明确 UWB 是车间双向测距，还是通过固定基站提供绝对位置。
- [ ] 确认 UWB 是否能输出原始距离、接收功率、信道脉冲响应（CIR）或 LoS/NLoS 质量信息。
- [ ] 明确实验真值来源：动捕、全站仪、AprilTag、人工测量控制点，或仅有相对距离真值。
- [ ] 记录虚拟机和两辆车的 CPU、内存与网络接口，提前判断融合节点应运行在车端还是上位机。
- [ ] 为两辆车指定固定名称：`car1` 和 `car2`。

验收结果：形成一张设备表，至少包含 IP、串口、传感器话题、频率和坐标系。

## 3. 阶段一：分别验证两辆单车

先保证每辆车单独工作正常，避免在双车系统中混合排查硬件故障和网络配置问题。

### 车 1

- [ ] 可以通过 SSH 登录。
- [ ] 可以正常启动底盘驱动。
- [ ] 键盘发送速度指令后，车辆运动和停止正常。
- [ ] `/odom` 连续发布，位置和航向变化方向正确。
- [ ] `/imu` 连续发布，静止时数据稳定。
- [ ] `/scan` 正常发布且雷达方向正确。
- [ ] 保存一次短 rosbag，包含速度指令、里程计、IMU、激光雷达和 TF。
- [ ] 保存 `rosnode info`、`rostopic hz`、`rostopic delay` 和 TF 检查结果，作为单车基线记录。

### 车 2

- [ ] 完成与车 1 相同的检查。
- [ ] 检查两辆车是否使用了相同的固定串口名称。
- [ ] 检查雷达或底盘设备是否会在重启后从 `ttyUSB0` 变成 `ttyUSB1`。

验收结果：两辆车均可单独连续运行 10 分钟，不出现驱动退出、串口冲突或话题中断。

## 4. 阶段二：建立双车 ROS 网络

### 网络

- [ ] 将虚拟机网络模式设置为桥接模式。
- [ ] 让虚拟机、车 1 和车 2 接入同一个局域网。
- [ ] 分别设置固定 IP，避免重启后地址改变。
- [ ] 验证三台系统可以相互 ping 通。
- [ ] 检查防火墙和路由器是否阻止 ROS 端口通信。

### ROS1 多机配置

- [ ] 在虚拟机上运行公共 ROS Master。
- [ ] 两辆车的 `ROS_MASTER_URI` 均指向虚拟机。
- [ ] 每台设备的 `ROS_IP` 设置为自己的实际 IP。
- [ ] 从虚拟机查看两辆车的节点和话题。
- [ ] 使用 chrony 或等效工具进行时间同步。
- [ ] 比较三台系统的时间，记录最大偏差。

建议地址示例：

```text
虚拟机  192.168.1.100
car1    192.168.1.101
car2    192.168.1.102
```

验收结果：两辆车同时运行时，虚拟机可以稳定接收两车的数据，时间戳持续递增且无明显时间跳变。

## 5. 阶段三：命名空间与 TF 隔离

### 话题命名

- [ ] 将车 1 的节点放入 `/car1` 命名空间。
- [ ] 将车 2 的节点放入 `/car2` 命名空间。
- [ ] 检查速度、里程计、IMU、激光雷达和 UWB 话题是否全部隔离。
- [ ] 确认向 `/car1/cmd_vel` 发指令时，车 2 不运动。
- [ ] 确认向 `/car2/cmd_vel` 发指令时，车 1 不运动。

建议话题：

```text
/car1/cmd_vel    /car1/odom    /car1/imu    /car1/scan    /car1/uwb/range
/car2/cmd_vel    /car2/odom    /car2/imu    /car2/scan    /car2/uwb/range
```

### TF 坐标系

- [ ] 按 [REP-103](https://www.ros.org/reps/rep-0103.html) 检查单位、轴向和右手坐标系。
- [ ] 按 [REP-105](https://www.ros.org/reps/rep-0105.html) 明确 `map`、`odom`、`base_link` 的职责，不能把连续但漂移的 `odom` 当作全局真值。
- [ ] 建立 `car1/odom -> car1/base_link -> car1/sensor_link`。
- [ ] 建立 `car2/odom -> car2/base_link -> car2/sensor_link`。
- [ ] 消除重复的 `base_link`、`odom` 和传感器 frame 名称。
- [ ] 使用 TF 工具检查是否存在断链、多父节点或时间外推错误。
- [ ] 在 RViz 中同时显示两辆车的模型和传感器数据。

验收结果：两辆车可以同时受控，话题和 TF 不冲突，任何一辆车重启都不会影响另一辆车。

## 6. 阶段四：建立无 UWB 定位基线

### 轮式里程计与 IMU

- [ ] 理解轮式里程计的位姿、速度和协方差字段。
- [ ] 检查 IMU 的单位、轴向、安装方向和静止偏置。
- [ ] 检查 IMU 消息中的姿态、角速度、线加速度协方差是否有效，不能用全零协方差假装“完全精确”。
- [ ] 采集一段长时间静止 IMU 数据；若需要估计白噪声和随机游走，参考 [`imu_utils`](https://github.com/gaowenliang/imu_utils) 做 Allan 方差分析。
- [ ] 测量车轮半径、轮距或麦克纳姆轮底盘参数。
- [ ] 完成直行、原地转动和闭环轨迹测试。
- [ ] 配置 `robot_localization` 的 EKF，融合轮式里程计与 IMU。
- [ ] 依据 [`robot_localization` Melodic 文档](https://docs.ros.org/en/melodic/api/robot_localization/html/index.html) 固定输入变量、`two_d_mode`、频率、超时和协方差配置，并为两辆车各保存一份 YAML。
- [ ] 对比原始里程计轨迹和 EKF 输出轨迹。

### 已知地图中的独立定位

- [ ] 在共享二维地图中分别运行两套 AMCL。
- [ ] 为两辆车分别设置初始位姿。
- [ ] 建立共享 `map` 到两车独立 `odom` 的变换关系。
- [ ] 记录无 UWB 情况下两辆车的定位结果，作为独立定位基线。

验收结果：两辆车可以在同一张地图中独立定位。该阶段仍不称为协同定位。

## 7. 阶段五：UWB 单独接入与标定

### 驱动和数据接口

- [ ] 为每个 UWB 节点设置唯一 ID。
- [ ] 记录 UWB 与对应车辆之间的安装位置。
- [ ] 建立 `base_link` 到 `uwb_link` 的静态变换。
- [ ] 将原始测距发布为带时间戳、节点 ID 和距离值的 ROS 消息。
- [ ] 测距消息至少包含 `stamp`、`source_id`、`target_id`、`range_m` 和 `variance`；设备支持时另外保留 RSSI、CIR、序列号与质量标志。
- [ ] 将设备原始串口记录与转换后的 ROS 消息同时保存，避免驱动预处理后无法重新标定。
- [ ] 检查测距频率、延迟、丢包率和异常值。

### 标定实验

- [ ] 在多个已知距离下采集静态数据。
- [ ] 计算每个距离下的均值、标准差和系统偏差。
- [ ] 分别测试无遮挡、人体遮挡和车辆遮挡。
- [ ] 明确标注 LoS、软遮挡和硬 NLoS，不把所有大误差简单归为高斯噪声。
- [ ] 测试车辆静止、低速运动和转弯条件。
- [ ] 检查距离、相对朝向、天线高度和运动速度是否改变偏差或丢包率。
- [ ] 确定异常值阈值或稳健滤波方法。
- [ ] 先保留“原始数据、常数偏差修正、异常值拒绝”三组结果；复杂 NLoS 分类器只在数据支持时再做。

重要限制：如果只有两车之间的一条 UWB 距离，它只能提供一个标量距离约束，不能单独确定两辆车各自的二维位置和航向。系统仍需要轮式里程计、IMU、地图定位、固定 UWB 基站或其他绝对约束。

验收结果：得到 UWB 误差统计、数据质量结论和可复用的 ROS 测距话题。

## 8. 阶段六：离线协同定位

先使用 rosbag 离线实现，确认数学模型和时间同步正确后再转为实时系统。

- [ ] 同步记录两车里程计、IMU、TF、控制指令和 UWB 测距。
- [ ] 统一所有测量的时间戳和坐标系。
- [ ] 在接入 rosbag 前，用合成二维轨迹和合成 UWB 距离完成观测模型、雅可比和噪声单位测试。
- [ ] 建立车间距离观测模型：`z12 = ||p1 - p2|| + noise`。
- [ ] 第一版先实现集中式二维 EKF；仅在状态、雅可比和可观测性检查通过后，再实现小型因子图对照。
- [ ] 因子图版本可参考 [GTSAM](https://github.com/borglab/gtsam) 的 `BetweenFactor<Pose2>`、`RangeFactor` 和稳健噪声模型，不从大型协同 SLAM 框架开始改。
- [ ] 输出两辆车在统一坐标系中的轨迹和协方差。
- [ ] 加入 UWB 异常值拒绝或稳健权重。
- [ ] 对比无 UWB 与加入 UWB 的定位结果。
- [ ] 检查不可观条件，避免把不能由观测确定的状态误认为可估计。
- [ ] 分别检查全局平移、全局航向和镜像/几何退化等自由度；说明哪些状态由初始先验、地图或固定基站约束。
- [ ] 不把单条非线性 UWB 距离伪装成绝对位置后直接送入 `robot_localization`；应在自定义协同滤波器或距离因子中处理。

验收结果：同一 rosbag 可重复得到一致结果，并能解释 UWB 在哪些轨迹和误差条件下改善定位。

## 9. 阶段七：在线协同定位与控制

- [ ] 将离线融合程序改为实时 ROS 节点。
- [ ] 处理测量延迟、乱序和短时丢包。
- [ ] 在 RViz 中实时显示两车轨迹、相对距离和置信范围。
- [ ] 同时显示实测距离与估计距离的实时残差，便于发现节点ID、时间戳或坐标系错误。
- [ ] 当 UWB 暂时失效时保持系统稳定运行。
- [ ] 恢复 UWB 后避免位置突跳。
- [ ] 根据定位结果进行低速双车运动测试。
- [ ] 设置急停方式并限制初期测试速度。

验收结果：系统连续运行 20 分钟，单个节点短时掉线不会导致两辆车失控或整个定位系统退出。

## 10. 实验场景与评价指标

### 场景

- [ ] 两车静止，不同已知间距。
- [ ] 一车静止，一车直线运动。
- [ ] 两车平行运动。
- [ ] 两车相向和交叉运动。
- [ ] 两车闭环运动并返回起点。
- [ ] UWB 遮挡、丢包和异常值注入。
- [ ] 轮式里程计打滑或人为增加漂移。
- [ ] 通过关闭一辆车的地图定位或减少绝对更新，验证 UWB 在不同先验条件下是否真的提供帮助。

### 对比组

- [ ] 轮式里程计。
- [ ] 轮式里程计与 IMU 融合。
- [ ] 独立定位基线。
- [ ] 独立定位加 UWB 协同约束。
- [ ] UWB 协同约束加异常值处理。

### 指标

- [ ] 绝对轨迹误差 ATE。
- [ ] 相对位姿误差 RPE。
- [ ] 位置和航向 RMSE。
- [ ] 车间距离残差。
- [ ] UWB 更新频率、延迟和丢包率。
- [ ] 定位中断后的恢复时间。
- [ ] 算法运行频率和 CPU 占用。
- [ ] 估计协方差的一致性或覆盖率；若尚无可靠真值，则不声称协方差或“完好性”已得到验证。
- [ ] 使用 [`evo`](https://github.com/MichaelGrupp/evo) 统一计算 APE/ATE 与 RPE，并保存对齐方式、时间关联阈值和命令行。

### 真值与评价边界

- [ ] 真值只用于生成受控观测和离线评价，不作为未声明的在线融合输入。
- [ ] 如果 AMCL 同时作为定位输入，就不能再把同一 AMCL 输出称为独立真值。
- [ ] 同时报告“固定初始参考、不做整段最优对齐”的绝对漂移结果，以及常见的对齐后 ATE；说明两者用途不同。
- [ ] 至少重复三次实车实验并保存失败运行，不只选择最好的一次演示。

## 11. 公开数据集与外部基准

公开数据集用于检查算法、接口和评价流程，不能替代两辆 ROS Car 的实测验证。当前采用“一套主数据 + 一套辅助数据”的策略。

### 主数据：LUCOOP

- [ ] 阅读 [LUCOOP 数据集说明与论文入口](https://data.uni-hannover.de/dataset/lucoop-leibniz-university-cooperative-perception-and-urban-navigation-dataset)。
- [ ] 先检查 README、许可、标定和一段最小样本，不直接下载全部数据。
- [ ] 选取其中两辆车，仅提取 IMU、LiDAR、V2V/V2X UWB、参考轨迹和必要标定。
- [ ] 用它验证数据解析、UWB残差、时间关联和轨迹评价脚本。
- [ ] 记录与本项目的差异：道路车辆、GNSS可用、缺少本车轮编码器、运动尺度不同。

### 辅助数据：按问题二选一

- [ ] 若重点是“相机/IMU/LiDAR/UWB紧耦合”，选 [NTU VIRAL](https://github.com/ntu-aris/ntu_viral_dataset)；它提供 ROS bag、标定和高精度真值，但平台是无人机且数据量较大。
- [ ] 若重点是“经典多机器人相对观测与协同定位”，选 [UTIAS MR.CLAM](https://asrl.utias.utoronto.ca/datasets/mrclam/)；它更适合理解算法和观测模型，但不是 UWB 数据。
- [ ] [S3E](https://pengyu-team.github.io/S3E/) 和 [MILUV](https://www.decar.ca/miluv/) 暂列后期选读：二者包含多机器人与UWB信息，但主要为 ROS2/无人机或更复杂多模态配置，不作为本月必需下载项。

验收结果：至少一套公开数据完成“字段说明—解析—一组基线—指标输出”的闭环，并写明不能迁移的假设。

## 12. 建议的六周安排

| 周次 | 工作重点 | 交付物 |
| --- | --- | --- |
| 第 1 周 | 单车复现、设备清点、网络配置；阅读 REP-103/105 | 设备表、单车测试 rosbag、坐标系说明 |
| 第 2 周 | 双车 ROS 网络、命名空间和 TF；阅读协同定位基础 | 双车 launch 配置、TF 图、时间同步记录 |
| 第 3 周 | 轮式里程计与 IMU 基线；检查公开数据最小样本 | EKF 配置、基线轨迹、数据字段表 |
| 第 4 周 | UWB 驱动、标定、LoS/NLoS误差统计 | 原始与处理后UWB数据、标定报告 |
| 第 5 周 | 合成单元测试、离线协同定位和对比实验 | EKF/距离因子测试、轨迹对比结果 |
| 第 6 周 | 在线融合、鲁棒性测试、公开数据交叉检查 | 演示、实验报告、复现说明和限制清单 |

## 13. 建议仓库结构

```text
docs/                  设计说明、设备表、实验记录
launch/                双车启动和定位启动文件
config/car1/           车 1 参数
config/car2/           车 2 参数
src/                   协同定位和 UWB 接口代码
scripts/               标定、评估和绘图脚本
results/               小型结果表和图
bags/                  本地 rosbag，不提交到 Git
datasets/README.md      公开数据的许可、下载、校验和预处理说明
references.bib          实际阅读和引用的论文，不堆放未读条目
third_party/README.md   借鉴仓库、固定版本、许可证和本地修改记录
```

每完成一个阶段，应同时保存启动命令、参数版本、数据来源、测试日期和已知问题。大型 rosbag、地图缓存和编译目录不直接提交到 GitHub。

## 14. 参考资料使用原则

- [ ] 先完成 [双车协同定位资料目录](roscar_reference_catalog.md) 中的“本月必读/必用”，再考虑大型多机器人 SLAM 框架。
- [ ] 论文用于支撑观测模型、可观测性、误差处理和实验设计；仓库用于借鉴接口与实现，二者不能互相替代。
- [ ] 每个第三方仓库记录 commit/tag、ROS版本、许可证、运行状态和本项目修改，不能只保存一个网址。
- [ ] “可以编译”“可以回放”“在本车上验证”“结果优于基线”是四种不同状态，分别记录。
- [ ] 未经本项目实测，不在清单或PPT中写“厘米级”“显著提升”或“鲁棒完好性”等结果性表述。
